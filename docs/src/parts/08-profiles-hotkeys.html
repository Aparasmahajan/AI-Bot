12Profiles, effort and models

Rev G: profiles, calibration, effort levels and the setup screen are Phase 5 and not built yet. On this laptop MWB runs as Lean with fixed settings from mwb\config\default.toml (§16.3).

The same code runs on every machine. A profile decides which models it uses, how many threads they get and what stays warm. An effort governor decides how hard MWB works from minute to minute (§12.5), and MWB re-tunes itself when you move it to another laptop (§12.6).

12.1Detection and calibration

  1. Probe at start-up: total and free RAM, number of memory sticks and their speed (which gives bandwidth), GPU and VRAM (DXGI, plus nvidia-smi when present), any NPU (device class ComputeAccelerator), CPU features such as AVX-512 VNNI, and the power source.
  2. Calibrate once, in about 60 s, and again whenever the hardware changes: speech speed on a bundled clip, the API's response time, tokens per second for the local fallback model on a fixed prompt, and typical free memory.
  3. Pick a profile and write it to the config. You can override it, for example profile = "lean".
  4. Choose models from models.yaml, which lists candidates for each capability, best first. The first one that fits the profile and passes the memory guard wins.

12.3Why the second memory stick matters

Writing each token means reading the whole model from RAM once, so tokens per second is at most usable bandwidth divided by model size. With one stick, roughly 19 of the theoretical 25.6 GB/s is usable; with two, about 38. People read at roughly 5 to 7 tokens per second. This is also why language work goes to the API for now: on one stick Qwen3.5 2B writes 10.3 tokens per second and 4B 3.6 (measured), while a hosted model such as Groq's writes hundreds.

You choose the level

On every new device, a setup screen shows what MWB found and pre-selects the suggested level. You can keep it or pick another. You decide four things: a fixed level, or automatic adjustment within a range you set; what happens on battery; a different level for any feature, for example High for the journal and Balanced for dictation; and whether to download the models your choice needs now or later. Levels the hardware can run, but slowly, come with a warning. Levels it cannot run at all are greyed out with the reason. The choice is saved for that machine only, and Settings → Performance reopens the same screen at any time.

How automatic adjustment works

  • Suggested level by profile: Lean E2, with E3 for the night pass; Balanced E3; Performance and Workstation E4. This is only the starting point on the setup screen.
  • Down, when automatic is on: one level on battery and two below 30 % charge; one level when the CPU stays above 80 % for 30 s or free memory drops below 2 GB. It never goes below the lowest level you set.
  • Up, when automatic is on: one level when on AC power, idle for 10 minutes and with room in memory, never above the highest level you set.
  • Fixed level: the rules above are off, except the memory guard (§11.2), which still defers work rather than let MWB run out of memory.

12.6Running on another laptop

Settings are split in two. What belongs to you travels with the app: hotkeys, dictionary, snippets, the per-app recording policy, privacy choices and, if you copy it, your history. What belongs to the machine never travels: profile, your effort choice for that machine, thread counts, model choices and calibration results. MWB works those out on the machine itself and files them under a hardware fingerprint built from the CPU model, RAM size and channels, GPU and VRAM, and any NPU.

  1. Install MWB on the new laptop, or copy the portable folder. Copy %APPDATA%\MWB for your settings and, if you want your history, %LOCALAPPDATA%\MWB\mwb.db and Documents\MWB\journal.
  2. On first start the fingerprint is new, so MWB calibrates for about a minute and opens the setup screen (Figure 12.3). It shows what it found and pre-selects a suggested profile and effort level, and you choose. It then lists the models your choice needs, with download sizes.
  3. It downloads them after you confirm and reuses any already on the machine, such as files in the Hugging Face cache.
  4. Optionally, run the night second pass over the last 30 days so older meetings get the better model's transcripts and notes.

Adding the second memory stick to this EliteBook takes the same path: the next start sees 32 GB in dual channel, suggests Balanced, and lets you choose again.

If you always want, for example, the highest level a machine can run, say so once with effort_preference = "max-available" in your own settings. Every new device then pre-selects that on its setup screen, and you still confirm it.

How the local model is kept in sync

  1. One set of prompts, one output check. Each skill has a single prompt template and a single JSON schema. The citation validator and the SHA check run on answers from both routes.
  2. One contract. The API and llama-server both speak OpenAI-compatible chat completions, so the router changes only the address and the model name.
  3. A sync check. Ten saved test prompts, one or two per skill, run through both routes in Phase 0, after any change to a prompt or a model, and once a week on AC power. As built, the core starts docs/bench/p0_4_sync_check.py once a week on mains power with the CPU under 60 %; the script skips the local half when memory is short, and writes its results to docs/bench/p0_4/. Showing the result on the Today page is still to do.
  4. Automatic fallback. When the API fails (no network, no word within 20 s, a rate limit, a bad key or no key), the same request goes to the local model if the memory guard allows it. A result panel that was already streaming starts again and says the local model is writing. If the local model can't load, the result panel says why, and a batch job waits and is tried again every 10 minutes.
  5. Local-only skills. Any skill can be set to local-only in Settings, and its text then never leaves the laptop. Learning your email style starts that way, because it reads 30 sent emails at once.
  6. Going local later. On a laptop with more memory, moving a skill to the local route is one setting, and the local model can grow to Qwen3.5 9B.

The trade-off. The API makes language work fast, a paragraph in 1 to 2 s against 5 to 15 s locally, and keeps MWB near 1 GB. In return, the text of your notes, email, code and journal goes to the API provider. Audio never does. On 13 October you said work text may go to Groq. Any skill can still be set to local-only, or pointed at a company Azure OpenAI endpoint. MWB's database logs each request's size, route and time, never its text. Groq no longer offers Qwen, so the two routes use different model families, and the sync check is what keeps their output consistent. Keys are kept in Windows Credential Manager, the same DPAPI protection AI-App uses.

A longer, plain-language guide to these models, written for someone new to AI, is in MWB\docs\MWB-QA.md under question 7.

13.1How the keys are wired

  • No keyboard hook. Shortcuts are registered with the Win32 RegisterHotKey call and MOD_NOREPEAT. MWB never sees any other keystroke, so Defender has nothing keylogger-like to flag.
  • Double taps. Caps Lock and Alt can't be registered as shortcuts without breaking their normal use, so the core checks the up and down state of only these two keys every 15 ms (GetAsyncKeyState). It cannot see any other key. Two clean taps within 350 ms count as a double tap. Caps Lock is put back to the state it had before the first tap, so the light never ends up changed. A single Alt tap still reaches your app as usual; in Office it briefly shows the key tips, and the second tap hides them again. Phase 0 task P0-2 checked that a 15 ms check catches at least 99 % of taps: it caught 50 of 50 for each key on 14 October, so no keyboard hook is needed.
  • Hold detection. After a hold shortcut fires, the core polls GetAsyncKeyState every 15 ms, only while the key is down, to see when you let go. For Ctrl+Alt+E, K and R, a press shorter than 0.35 s is a press (explain); holding longer starts listening.
  • Conflicts. Each binding has a fallback list and logs [hotkey] ctrl+alt+k could not be registered when another app owns it, the same pattern as AI-App's tryRegister().
  • Starting MWB. Setup adds a Start-menu shortcut with Ctrl+Alt+W as its shortcut key. Windows handles that key itself, which is why it works before MWB is running.
  • AltGr keyboards. On layouts where Ctrl+Alt acts as AltGr, give each shortcut a Ctrl+Shift+Alt fallback in [hotkeys]; each binding is a list, and the first one Windows accepts wins.
  • Wispr Flow. Turn it off before using MWB dictation, so only one app owns the mic and the push-to-talk keys.

13.3On-screen indicator

Like the small pill Wispr Flow keeps at the bottom of the screen, MWB can show a floating indicator that tells you at a glance what it is doing. It sits 48 px above the taskbar on the screen you are working on, lets clicks pass straight through (except on an open result panel), and never takes the keyboard focus, so your text still lands in your app. Double-tap Alt to show or hide it. MWB keeps working either way, and the tray icon still shows the state.

Results in the indicator's place. Answers, email and reply drafts, code explanations and rewrites open where the indicator is, as in Wispr Flow, not in a separate window. While MWB works, the pill shows three amber dots; then a dark panel, 440 px wide at 100 % scale, fades in and rises out of the pill, and the text streams into it. Up to nine lines show at once; the mouse wheel scrolls a longer answer, and a soft fade shows there is more above or below. The buttons sit in the panel's footer, with the main one on the right in blue.
