8Architecture

8.1Design principles

  1. A small core that is always on, and disposable workers for heavy work. On Windows, ending a process is the only dependable way to return its memory.
  2. Speech local, language through an API for now. Audio never leaves the laptop. Language work goes to an API so it needs almost no memory, and a local model kept in sync takes over when the API can't be used. Any skill can be set to local-only, and MWB shows exactly what it sends.
  3. Facts by code, prose by model. SHAs, durations, counts and names come straight from the database. The model writes only the narrative, and each sentence must cite the events it describes.
  4. Every engine behind an interface. Swapping Parakeet for Granite Speech, the API for a local model, or a 2B model for a 9B one, is a configuration change.
  5. Visible and in your control. Tray state, a recording indicator and one key that pauses everything.
  6. Effort follows the hardware. The same build works harder on a stronger machine, and moving it to another laptop re-tunes it on first start (§12.5, §12.6).
  7. No vendor lock-in for calls. Any app that holds the microphone can be a meeting; a registry file names the known ones (§9.3).

8.4Interfaces

Workers speak plain HTTP on 127.0.0.1 with a random port and a per-session token, the same pattern AI-App uses for its speech sidecar. Any engine that speaks the same contract can be dropped in.

Worker contracts
# Speech worker. Same contract as AI-App's server.py and whisper-server.
POST /inference      multipart/form-data, field "file" = 16 kHz mono 16-bit WAV
                     optional fields: lang = en | hi | auto, lane = me | them
  -> 200 {"text": "...", "engine": "parakeet-int8", "audio_s": 4.2, "ms": 910}
GET  /health         -> {"ok": true, "model": "nemo-parakeet-tdt-0.6b-v2", "private_mb": 990}
POST /shutdown       -> process exits; the core restarts it on the next request

# Language: the API (Groq by default) or the local llama-server. Same contract, so the router switches freely.

8.6The running loop

MWB does not spin in a loop checking things all the time. The core spends almost all of its life asleep inside one Windows message loop. It wakes only when something happens: a key tap, a hotkey, a timer, a power or audio-device change, or a click on the tray icon. Each wake-up takes microseconds, so the core uses close to 0 % CPU while you work. Heavy work never runs inside the loop; the loop hands it to a background thread or a worker process and goes straight back to sleep.

One round of use, from a double tap of Caps Lock to text in your app or an answer on screen, goes through the steps below. The details are in §9.1 and §9.7.
